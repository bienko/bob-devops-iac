    MONITORING AND OBSERVABILITY

    i. WHAT YOU WILL OBSERVE

    Christopher Bienko (AI Enablement GTM Product Manager) provides an overview of the Operate - Monitoring and Observability module for the hands-on enablement. [1 min]

    AI MATURITY CURVE

    Take note of what this module asks of you. Bob built the observability stack in Module 1 and deployed it in Module 2. Here you verify, with your own queries, that it reports the truth. The previous course made the same demand at every stage: delegated work earns trust through evidence.

    USE THE TERMINAL RATHER THAN BOB SHELL

    Module 3's commands are plain shell commands. They go at the regular prompt in the Bob IDE terminal rather than into Bob Shell. If Bob Shell is still open from Module 2, exit it first. The SSH tunnels stay up: they run as a background process, independent of Bob Shell.

    In this part you log into each UI and read the dashboard that was provisioned for you. You then generate traffic and watch the panels move. Finally, you query metrics and logs directly. Everything happens in two places: your browser for the UIs, and the Bob IDE terminal for the occasional command.

    Everything is reached through the SSH tunnels Bob Shell opened during deployment. Nothing is publicly exposed, and there are no make targets for any of this. If the tunnels are down, reopen them as in Automated Deployment.

    iii. HOW THE PIECES FIT

    Two pipelines run side by side and never touch each other. Prometheus handles the numbers — request counts, latencies, and failure counts. Loki handles the lines: the actual log output of every container. Grafana is the only thing that sees both, and it collects nothing itself; every panel is a query it sends to one of them.

    Collects Stores in You read it through
    Prometheus numbers scraped from /metrics endpoints Prometheus Grafana panels, or the Prometheus UI on :9090
    Promtail → Loki log lines from container stdout/stderr Loki Grafana → Explore

    You need both because a metric tells you that something happened and a log tells you what. When the error rate climbs, Prometheus cannot tell you which URL failed: a counter has no room for that detail. Loki has the line, GET /does-not-exist 404, with the client address and the duration.

    PROMETHEUS IS THE DATABASE

    Stop Prometheus and the dashboard goes blank. Stop Grafana and the data keeps accumulating regardless.

    In more detail:

    • Prometheus scrapes two jobs every 15 seconds (prometheus.yml.j2): itself at localhost:9090, and Traefik at traefik:8080/metrics over the private Rancher network; no host port is involved in the scrape.
    • Grafana is provisioned from files rendered by Ansible. Two datasources are defined: Prometheus (the default, at http://prometheus:9090) and Loki (at http://loki:3100), both marked non-editable. One dashboard is loaded from /etc/grafana/dashboards.
    • Promtail discovers running containers through the Rancher socket and tails their stdout/stderr. It labels each stream with container_name, compose_service and host, then pushes to Loki. Its pipeline strips ANSI colour codes and parses the timestamp out of Traefik's access log lines so Loki stores the real log time rather than the ingest time.
    • Loki runs single-process with filesystem storage on the loki_data volume and a 31-day retention window (loki_retention_period: 744h).

    There is no Alertmanager: the Prometheus template ships with the alerting: block commented out and rule_files: []. This lab visualizes; it does not page anyone.

    iv. THE PRE-PROVISIONED DASHBOARD

    1. In the Grafana tab, log in as labadmin with your TF_VAR_grafana_admin_password.
    2. In the left sidebar, choose Dashboards → Browse.
    3. Click Traefik Overview.

    This step is about understanding rather than doing. There is nothing to run here; simply read what the dashboard is already showing you.

    The panels are not empty, even on a stack nobody has used yet. Prometheus scrapes Traefik every 15 seconds and Traefik pings its own healthcheck, and both of those are requests through Traefik, so Traefik counts them. Check the legend on the request-rate panel: the flat baseline series is labelled traefik, the entrypoint the monitoring stack talks to. The web entrypoint, the one a real user arrives on, sits at zero until Step 3.

    A PANEL READING OF NO DATA INDICATES A BUG

    Nothing here exports container or host metrics, so a panel asking for CPU or memory (container_cpu_usage_seconds_total and similar) can never have data to show. If you see one, the dashboard is querying a metric this stack does not collect. Ask Bob to fix the panel rather than assuming your platform is broken.

    Bob writes this dashboard fresh on every run, so your panel titles will not match anyone else's word for word. Rather than trust a list here, read the query behind any panel yourself: hover the panel, press E, and look at the query box.

    Whatever the titles say, every run shows the same four things:

    • Request and error rates come from Traefik's own counters (traefik_entrypoint_requests_total or traefik_service_requests_total, split by code). Apache exports no metrics of its own, so the Apache view is Traefik's per-service counters. Every request reaches Apache through Traefik, so nothing is missed.
    • Response time comes from histogram_quantile over ..._request_duration_seconds_bucket, usually at p50, p95 and p99.
    • Open connections come from traefik_..._open_connections.
    • Anything named for Prometheus (scrape duration, scrape samples) is Prometheus reporting on its own scraping rather than on your app.
    • A Loki logs panel, if your run built one, showing Traefik's access log lines.

    v. GENERATING TRAFFIC

    Everything on the dashboard so far is the stack watching itself. These two loops add traffic on the web entrypoint, the path a real user takes, and deliberately break some of it.

    1. Paste this whole block into the Bob IDE terminal; the two loops run one after the other:

      # 100 successful requests
for i in {1..100}; do curl -s http://localhost:8080/ > /dev/null; done

# 20 requests to a path that doesn't exist
for i in {1..20}; do curl -s http://localhost:8080/does-not-exist > /dev/null; done

      The commands print nothing; their effect shows up on the dashboard. Each loop serves a purpose:

      • The 100 successful requests prove the whole path works end to end, laptop → SSH tunnel → host loopback → Traefik → Apache, and they separate real traffic from the monitoring noise by landing on a different entrypoint.
      • The 20 deliberate 404s give you a failure to look at. Without them the error panel stays at zero and you learn nothing from it. They also plant something specific for Loki to find in section vii, which is the difference between "errors went up" and "someone requested /does-not-exist twenty times".

    1. Switch back to the Grafana tab and set the refresh picker (top right) to 5s. Within a scrape interval or two (15 s), watch for three changes:

      • The request rate panel climbs off the floor, and the total-requests counter jumps by 120
      • The rate panel splits into two series, one for 200 and one for 404, since the second loop asked for a page that isn't there
      • The error rate panel moves off zero. If your run also has a 5xx-only panel, it stays flat: a 404 is a client error rather than a server error, and that distinction is precisely why the two are separated
      • If you have a Loki logs panel, the same requests appear in it line by line

    vi. QUERYING PROMETHEUS DIRECTLY

    1. In the Prometheus tab (http://localhost:9090), open Status → Target health. There are two required targets, and both must show UP:

      Job Endpoint
      prometheus localhost:9090/metrics always
      traefik traefik:8080/metrics always
      loki loki:3100/metrics if your Step F run added a scrape job for it

      prometheus and traefik must both be UP; those two carry the whole dashboard. A third loki target is also correct — Loki reports on itself, and some runs wire up a scrape job for it in Step F. What must not appear is an exporter for Apache: Apache publishes no metrics of its own, and every request reaches it through Traefik, so Traefik's per-service counters already measure it.

      TROUBLESHOOTING: the traefik target shows DOWN

      Check the container and the metrics endpoint. Paste these into the Bob IDE terminal:

      ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "docker ps | grep traefik"
ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "curl -s http://127.0.0.1:8080/metrics | head"
    1. Run the dashboard's own queries by hand. These are the exact expressions behind the panels; running them here shows you the raw series underneath.

    Query 1: the status-code split

    1. Paste this into the expression bar and click Execute:

      sum(rate(traefik_service_requests_total[2m])) by (code)

      The Table tab gives one row per status code, and both of your loops are visible: a 200 series from the 100 successful requests and a 404 series from the 20 requests to /does-not-exist. The result is two rows — one per outcome — split by the code label that the by (code) clause requested.

      WHY THE VALUES READ 0

      rate(...[2m]) is not a total. It is the per-second average over the last 2 minutes, so it answers "how fast are requests arriving right now" rather than "how many have there ever been". The curl loops finish in seconds, and once they are more than 2 minutes in the past the window contains no requests at all, so the rate falls to 0 for both codes.

      The rows themselves are what matter: the series still exist, which proves Traefik counted the traffic and labelled it by status code. To see non-zero values, re-run the curl loops from section v and hit Execute again within 2 minutes. For the running totals instead, drop the rate() and query sum(traefik_service_requests_total) by (code) — those numbers only ever climb.

    1. Now click the Graph tab:

      The graph is the same data over time rather than at a single instant, and it shows what the table cannot: a flat line at zero, a spike where your loops ran, then a decay back to zero. The decay is the 2-minute window sliding forward — each scrape drops a little more of the burst out of range until none of it remains. Two coloured series appear, one per status code, with the legend naming them. This shape is exactly what the request-rate panel on the Grafana dashboard draws.

    Query 2: p95 latency

    1. Replace the expression with:

      histogram_quantile(0.95, sum(rate(traefik_service_request_duration_seconds_bucket[2m])) by (le, service))

      This one answers a different question: how slow is the slow end of your traffic? Traefik records durations into a histogram of buckets (le = "less than or equal to"), and histogram_quantile(0.95, ...) reads across those buckets to find the response time that 95% of requests came in under. The query uses p95 rather than an average because averages hide the bad tail: a handful of slow requests barely move a mean, yet they are exactly what users notice.

      The Table view gives one row per service, with the value in seconds — so 0.0025 means 2.5 milliseconds. Expect single-digit milliseconds here: the request never leaves the host, so there is no real network latency to measure, just Traefik forwarding to Apache over the private Rancher network.

    1. Switch to Graph for the same figure over time:

      The line appears only where traffic existed and gaps where none did — histogram_quantile has nothing to compute from an empty window, so it returns no value rather than zero. A gap here means "no requests" rather than "instant responses" — a distinction worth internalizing before you read the same panel in Grafana.

    vii. QUERYING LOGS IN GRAFANA EXPLORE

    The dashboard shows a fixed Loki view; Explore is where you query the logs freely.

    Open Explore

    1. In Grafana's left sidebar, click Explore (the compass icon).

      Explore is a scratchpad for ad-hoc queries. Unlike a dashboard panel, nothing here is saved or provisioned — you are querying the datasource directly.

    1. Choose Loki from the datasource dropdown at the top.

      It defaults to Prometheus, the default datasource for metrics. Loki holds the log lines, and the two answer different questions: Prometheus told you how many requests returned 404, Loki tells you which paths they asked for.

    Build the query with label filters

    1. Open the label dropdown and select container_name.

      This label exists because Promtail was configured to attach it to every stream. Without it every container's logs share one undifferentiated job label and you cannot ask about a single service.

    1. Select traefik as the value.

      The dropdown lists one entry per container Promtail is tailing, which doubles as proof that log collection is working across the stack.

    Run it

    1. Click Run query. The builder has assembled the LogQL you could equally have typed by hand:

      {container_name="traefik"}

    1. The results pane fills with Traefik's log lines, newest first.

      Two things are on screen. The histogram along the top bins log volume over time — the same burst you saw as a spike in Prometheus, now counted as lines rather than as a rate. Below it, the individual entries: click any line to expand its parsed fields.

      These are the same requests Prometheus counted, from the other side. The metric told you 20 requests returned 404; these lines name /does-not-exist as the path. That pairing — a number that tells you something is wrong, and a log line that tells you what — is the reason both halves exist.

    1. Run this to watch a different container entirely:

      {container_name="apache_web"}

    2. Click Live (top right), then re-run the curl loop from section v in the terminal, and watch log lines stream in as they arrive.

    viii. WHAT PERSISTS

    CHECKLIST

    Before moving on, verify the following:

    • Both Prometheus targets (prometheus, traefik) show UP
    • The curl loop moved Request Rate, the status-code split, and the error-ratio gauge
    • Access-log lines for your requests appear in the Loki panel and in Explore

    All three monitoring stores sit on named Rancher volumes, so they survive container restarts and re-deploys:

    • grafana_data: Grafana's DB. Any panel you edit or add in the UI persists here (allowUiUpdates: true in the provisioning config), while the provisioned dashboard file is re-read every 30 seconds.
    • prometheus_data: the Prometheus TSDB.
    • loki_data: Loki's chunks and index, pruned by the compactor after 31 days.

    Backing these volumes up and restoring them is covered in Self-Healing & Recovery.

    ix. KEY TAKEAWAYS

    • Prometheus holds the numbers and Loki holds the lines; Grafana queries both and stores nothing of its own.
    • Traefik's per-service counters are the only application metrics, since every request reaches Apache through Traefik.
    • rate() is a per-second average over a window rather than a running total, so a burst decays back to zero as the window slides.
    • p95 latency reveals the slow tail that an average conceals, and a gap in that series means no traffic rather than instant responses.
    • The container_name label exists because Promtail was configured to attach it; without it, no single service could be isolated in Loki.
    • All three monitoring stores live on named volumes and survive container restarts and re-deploys.
