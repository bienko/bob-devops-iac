    i. WHAT YOU WILL VALIDATE AND ADD

    Christopher Bienko (AI Enablement GTM Product Manager) provides an overview of the Design - Validation and Enhancement module for the hands-on enablement. [1 min]

    AI MATURITY CURVE

    This chapter contains the clearest illustration in the entire course of why the developer stays in control. In Step F, Bob begins building deliverables you have not asked for yet. Approving them is reasonable; approving them knowingly is the discipline. That judgment call is the same one you practiced throughout Module 2 | Delegate, and no amount of autonomy between the gates removes it.

    Module 1 | Architecture and Planning ended with an architecture, a Terraform layer, an Ansible layer, and a security review. In this second-half, you will define four more prompt-review cycles within the Bob IDE:

    • Step E — audit the code for idempotency, lint findings, and weak drift detection
    • Step F — extend the monitoring stack with Loki and Promtail
    • Step G — produce a disaster-recovery and rollback runbook
    • Step H — wire up a CI/CD pipeline and a matching local check target

    As in previous section, everything happens in Bob IDE on your laptop. Nothing is deployed until the Module 2 | Deploy chapters.

    ii. STEP E: IDEMPOTENCY, LINT, AND DRIFT AUDIT

    Before introducing any new functionality, ask Bob to verify that the existing codebase is both lint-clean and idempotent.

    A lint-clean codebase passes static quality checks without errors or warnings, while an idempotent deployment produces no changes when run repeatedly. The first execution may apply required updates, but a second execution should result in a no-op with zero additional changes.

    1. Click the task prompt field to start a new task.

    1. Select Plan mode. This step starts as a review, so Plan mode is the right posture: Bob reads and analyzes first, and nothing can change until you explicitly allow it.

    1. Paste the prompt below and send it:

      Run a static review against terraform fmt, terraform validate, tflint, ansible-lint and yamllint. Execute each tool as a real shell command and work from its actual output — do not reason about what a linter would probably report, and do not record a finding you have not seen a tool print. Use terraform fmt -check -recursive and ansible-lint with no path filter so nothing is skipped. If a tool is not installed, say so explicitly and mark that linter NOT RUN rather than simulating it. Fix every finding inline, then re-run every tool and paste the final output showing zero remaining failures. Then walk through what terraform plan should report on a second run (must be no-op) and what ansible-playbook --check --diff should report (must be 0 changed). Highlight any resource where drift detection is weak (null_resource, local-exec, manually-created host files) and propose stronger alternatives.

Propose those alternatives, do not build them. A checksum-and-assert mechanism layered on top of the existing tasks reports `changed` on every run, which breaks the idempotency proof it was meant to protect.

Leave the platform contract alone: container names, grafana_admin_user, the bootstrap and content tags, the /opt/lab paths, and the accepted risks recorded in Step D. If a linter flags one of them, say so and move on.

Then audit the observability contract, which linters cannot check. Extract every metric name referenced in the Grafana dashboard JSON and confirm each one is exported by a target configured in prometheus.yml, accounting for exporter flags that gate whole metric families and for label collisions that rename an exporter's labels. Extract every label selector used in Loki panels and confirm the log scraper's relabel config actually produces those labels. Report any panel whose query cannot resolve against the deployed configuration as a defect, with the specific config change that fixes it. A dashboard that renders "No data" on a healthy stack is a bug, not an empty state.

    iii. STEP F: ADD THE OBSERVABILITY STACK

    You cannot operate what you cannot see. Part 1 already gave you Prometheus and Grafana; this step adds the log side: Loki for aggregation and Promtail as the container logs scraper, turning the demo into a platform you can genuinely operate.

    1. Paste the following prompt (Bob stays in Agent mode) and hit Enter to execute:

      Extend the monitoring Terraform module and the monitoring_content Ansible role to add Loki for log aggregation and Promtail as a Docker logs scraper. Ansible renders /opt/lab/loki/loki-config.yml and /opt/lab/promtail/promtail-config.yml, and Terraform bind-mounts the parent directories /opt/lab/loki to /etc/loki and /opt/lab/promtail to /etc/promtail, read-only. Mount the directories, never the files. Configure Promtail so every log stream carries a container_name label; a shared job label alone makes containers indistinguishable and forces JSON parsing onto containers that do not emit JSON.

In the Loki compactor config, if you set retention_enabled: true you must also set delete_request_store: filesystem. Loki 3.x refuses to start without it and crash-loops with "CONFIG ERROR: invalid compactor config: compactor.delete-request-store should be configured when retention is enabled". Either set both or set neither.

Extend the dashboard Step C already created, in place, with the same filename, uid and title. The stack must end with exactly one provisioned dashboard, because Grafana's dashboard provider loads every file in the directory and a second one appears as a duplicate. Do not write a new dashboard file. It shows: Traefik request rate and 5xx ratio, Apache request rate, and a Loki panel with the last 100 Traefik access log lines. Make Grafana persist its DB on a named volume. Update outputs to expose grafana_url, prometheus_url and loki_url.

Before writing the dashboard, list the metric names each panel needs and confirm every one is actually exported by a configured scrape target. Do not emit a panel querying a metric you have not verified exists. If a panel would need an exporter this stack does not run, either add that exporter and its scrape job or leave the panel out, and say which you chose and why. Ratio panels must wrap the numerator in `or vector(0)` so they render 0 rather than "No data" when the numerator matches no series. The Loki panel must select by container_name so it reads one container's logs, and must filter out that container's own application log lines so only access log entries remain.

Every healthcheck you write must use a binary that actually exists in that container's image. The grafana/promtail image has no wget and no curl, so a wget-based test fails forever on a working container and Docker reports it unhealthy. Verify the binary is present before using it, and if the image ships no HTTP client, use a check that depends only on what is there.

    apply IS DELIBERATELY EXCLUDED FROM ci-local

    The Makefile has an apply target, but it is excluded from ci-local and asks for confirmation: applying is a change to the live environment and belongs behind the CI approval gate rather than in a local lint loop.

    Check before approving:

    • Workflow jobs match the prompt: validate, plan (PR comment), apply (environment approval)
    • The playbook --check --diff step targets a staging inventory
    • The token is least-privilege (contents: read by default)
    • make ci-local runs the same checks in the same order as the CI validate job

    vi. WHAT YOU JUST BUILT

    Across Steps A–H, a one-paragraph brief became:

    • A documented architecture (with a diagram)
    • Modular Terraform and Ansible code
    • A security and drift review
    • A full observability stack (Prometheus, Grafana, Loki, Promtail)
    • A disaster-recovery runbook
    • A CI/CD pipeline with a local make ci-local equivalent

    vii. KEY TAKEAWAYS

    • Bob's own report is never the proof; run the linters yourself, and treat a simulated pass as worse than no pass.
    • Idempotency is what makes Module 2's repeated runs safe, and the lifecycle blocks from Step B are what keep terraform plan a no-op.
    • Adding Loki and Promtail is one feature walking the entire Terraform chain, from module to root to example file.
    • When Bob expands scope on its own, approve knowingly: you are the only check on scope.
    • A runbook is held to a standard of recovery paths and a one-page TL;DR, and Bob rewrites rather than patches when the existing file falls short.
    • CI/CD comes in two halves — continuous validation on every push, and gated delivery behind a human approval — mirrored locally by make ci-local.
