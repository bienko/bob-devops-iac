    MODULE 2 | DEPLOY

    TESTING AND TROUBLESHOOTING

    i. WHAT YOU WILL VERIFY

    Christopher Bienko (AI Enablement GTM Product Manager) provides an overview of the Deploy - Testing and Troubleshooting module for the hands-on enablement. [2 min]

    AI MATURITY CURVE

    Take note of the division of labor in this chapter. Bob ran the validation once during deployment. Now you run it again yourself. The previous course called this the control beat: delegate the work, then verify the result before trusting it.

    The single prompt from Automated Deployment continued well past apply: its step 6 validated the whole platform through the tunnels before reporting success. This page covers the part you perform yourself. You open the services in your browser, then hand Bob one follow-up prompt to re-prove the two claims that matter most: the stack is idempotent, and the host has zero public web ports.

    Everything here runs against localhost on your laptop, which is precisely the design intent: the only path to the platform is the SSH tunnel Bob Shell opened in Step 5.

    ii. WHAT BOB VALIDATED

    There is nothing to run in this section. Step 6 of the deployment prompt validated the platform. It ran four HTTP checks through the tunnels — the app, the Traefik API, Grafana, and Prometheus. It also produced a remote docker ps listing and a port audit confirming that nothing binds to 0.0.0.0. If a service misbehaves once you start browsing, the two dropdowns below cover the usual causes.

    TROUBLESHOOTING: channel ... open failed: connect failed when curling localhost

    Cause: The tunnel is up, but the remote container is not yet listening on 127.0.0.1. Either it is still starting, or its ports block does not bind to loopback.

    Fix: Re-check what's running and listening on the host, and confirm ip = "127.0.0.1" in the Terraform ports block:

    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "docker ps"
ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "ss -tlnp | grep -E ':(80|3000|8080|9090)'"
    TROUBLESHOOTING: localhost:8080 works but localhost:3000 does not

    Cause: Grafana has not finished its first-boot database migration; the other services come up faster.

    Fix: Wait 15–20 seconds and re-curl http://localhost:3000/api/health. If it persists:

    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "docker logs grafana --tail 50"

    iii. VALIDATING THE PLATFORM

    After Bob Shell finishes, the tunnels are already up. Inspect the platform directly first, then hand the remaining proofs back to Bob.

    Open the services in a browser

    open http://localhost:8080      # the app
open http://localhost:3000      # Grafana (labadmin / $TF_VAR_grafana_admin_password)
open http://localhost:8081      # Traefik dashboard
open http://localhost:9090      # Prometheus

    The open command is specific for macOS. Use xdg-open on Linux.

    The app's landing page, served by Apache behind Traefik. The card itself confirms the design: lab_net network, 127.0.0.1 bindings only, provisioned by Ansible + Terraform:

    Grafana's login screen. Sign in with labadmin and your TF_VAR_grafana_admin_password:

    The Traefik dashboard opens straight to its router and service view, with no login required. Module 1 recorded that as an accepted risk rather than a finding: the dashboard is only reachable through your tunnel, so a password on it would protect nothing while hiding the credentials from you.

    TROUBLESHOOTING: the Traefik dashboard asks you to sign in

    Cause: The Step D audit ignored the accepted-risks block and put a BasicAuth middleware in front of the dashboard. It generated the password hash itself, so there is no credential to type. This is the most common way the lab goes wrong.

    Fix: Find the middleware and take it out, then re-apply:

    grep -rn 'basicauth\|users *=' infra/terraform infra/ansible
cd infra/terraform && terraform apply

    Then re-run the Step D audit with its accepted-risks block intact, so the middleware does not come back on the next pass.

    Prometheus opens straight to its query page with no login required. Reachability is its protection, since the only path to it is your tunnel:

    TROUBLESHOOTING: Grafana says invalid username or password

    Cause: TF_VAR_grafana_admin_password was not exported in the same shell that ran terraform apply, so Grafana was provisioned with a different password than the one you are typing. (Remember also that the username is labadmin rather than admin.)

    Fix: GF_SECURITY_ADMIN_PASSWORD only takes effect the first time Grafana initialises its database, and that database lives on a named volume that survives container replacement. So re-running terraform apply on its own will not change the password. Reset it in place instead:

    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "docker exec grafana grafana-cli admin reset-admin-password '<your-password>'"

    Then export the same value so future applies agree with it:

    export TF_VAR_grafana_admin_password='<your-password>'

    Log in as labadmin with that value. To start completely clean instead, remove the grafana_data volume and re-apply, which loses saved dashboards.

    Optional: have Bob re-prove the claims

    Give Bob Shell one follow-up prompt:

    Re-run terraform plan and ansible-playbook in --check mode and confirm 0 changes. Then show me that no port is bound to 0.0.0.0 on the host.

    Bob runs the same commands an operator would and reports back. Read its output against what must hold:

    • terraform plan reports No changes, meaning the real infrastructure matches the code.
    • The Ansible check run finishes with changed=0 in the PLAY RECAP.
    • The port listing on the host (ss -tlnp) shows every published port on 127.0.0.1, never 0.0.0.0. The cloud security group never changed: only SSH is exposed, and the internet cannot see this platform at all.

    This is what distinguishes infrastructure from a script — running it a second time does nothing, because nothing remains to converge. If Bob reports changes instead, that is drift, and the two most common causes are covered below.

    Killing a container to prove self-healing belongs to Self-Healing & Recovery. This page validates; Module 3 breaks things deliberately.

    TROUBLESHOOTING: terraform plan keeps showing N to add / N to destroy on a re-run

    Cause: The kreuzwerker/docker provider sees the daemon-injected log_opts (from daemon.json) and the image's USER / WORKDIR defaults as drift, and they forces replacement.

    Fix: Every docker_container resource needs:

    lifecycle {
  ignore_changes = [log_opts, user, working_dir, command]
}

    Re-apply once; after that, plan is a clean no-op.

    TROUBLESHOOTING: Ansible --check reports unexpected changed

    Cause: A Jinja template uses non-deterministic data (timestamps, random ids), so the rendered file differs on every run.

    Fix: Pin such values to variables so the rendered output is stable, then prove it:

    cd infra/ansible
ansible-playbook -i inventory.ini site.yml --check --diff --private-key "$SSH_KEY"

    --diff shows exactly which lines churn; that is the template to fix.

    iv. TEARING DOWN THE TUNNEL

    When you have finished demonstrating, terminate the multiplexed SSH session:

    pkill -f "ssh.*-L 8080:127.0.0.1:80.*${TARGET_HOST}"

    Matching on the forward and the host, rather than on ssh.*${TARGET_HOST} alone, means an interactive SSH session you have open to the same server survives.

    If a check fails instead, there is no need to debug from scratch. It might be channel open failed on a curl, Grafana rejecting the admin password, or bind: Address already in use when the tunnel starts. Each of those has a Troubleshooting dropdown next to the step that produces it — on this page and in Automated Deployment.

    v. KEY TAKEAWAYS

    • Bob's deployment prompt validated the platform once; the operator verifies it a second time, in person.
    • A clean terraform plan (No changes) and an Ansible check run with changed=0 are the proof of idempotency.
    • Every published port sits on 127.0.0.1, never on 0.0.0.0, and the security group exposes SSH alone.
    • The Traefik dashboard and Prometheus carry no login by design; reachability through the tunnel is their protection.
    • Grafana's admin password takes effect only at first initialization, so a mismatch is reset in place rather than re-applied.
    • Recurring plan churn and Ansible changed reports are drift, and each has a known cause documented beside the step that reveals it.

    The platform is deployed and validated. Continue to Monitoring & Observability to work with the Grafana and Prometheus stack, then to Self-Healing & Recovery to crash a container and watch Rancher's restart policy bring it back.
