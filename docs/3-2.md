## **ii. WHY A NAIVE CRASH DEMO FAILS**

Two facts make a naive "kill the container" demo fail, and both were designed around back in Module 1.

**1. `docker stop` and `docker kill` do not trigger the restart policy.** Docker treats them as **deliberate user stops**, and `restart: always` fires only on *unexpected* exits. Stop the container from outside and it remains in the `Exited (137)` state indefinitely. To prove real self-healing, the crash has to come from **inside** the container so the exit looks unexpected to the daemon.

**2. Linux protects PID 1 of a PID namespace from SIGKILL.** Even from inside, `docker exec apache_web kill -9 1` is a no-op: if httpd runs as PID 1, it is immune. This is why [Module 1 Step B](1-1.md#iii-step-b-generate-the-terraform-layer){:target="_blank"} rule (e) set `init = true` on the web container: Rancher injects **tini** as PID 1 (the `init` flag) and httpd becomes PID 2+, which *can* be killed. When httpd dies, tini exits with the same status, the daemon sees an unexpected crash, and `restart: always` brings the container back in a few seconds.

## **iii. RUNNING THE DEMO**

!!! info "THE DEMO WAS MADE POSSIBLE IN MODULE 1"
    Without `init = true`, nothing can be done at demo time to make this work — the remedy is a Terraform change and a re-apply. That single line is what makes the crash possible at all.

The demo consists of six short steps, all pasted into the Bob IDE terminal. You capture the before state and confirm the app is up. You crash it and wait. You then confirm the app is back, capture the after state, and compare.

    !!! note "WRITE DOWN YOUR `restartCount`"
        Your starting value depends on how many times the container has already come up; the screenshot above shows **4**. The absolute number is unimportant. What matters is that it has increased by **exactly 1** by the end of the demo.

        That precision is the claim being tested. **Exactly +1** means Rancher saw one unexpected exit and performed one restart — a clean, controlled recovery. **No change** means the crash never registered as unexpected and the restart policy did not fire. **More than +1** means the container is crash-looping — coming up broken and dying again each time — which is a failure that resembles a success at first glance.

        Keep this output on screen; you compare both values against it in *Confirm the app is back*.

### **Crash httpd inside the container**

3. The landing page HTML prints to the terminal — look for **"Welcome"** in the body.

    - That output travelled the full path the lab was built around.
    - It exited your local machine and passed through the SSH tunnel into the host loopback.
    - From there it went through Traefik to Apache and returned the same way. `-f` makes curl fail loudly on an HTTP error instead of printing an error page, so HTML on screen means a genuine 200.

    Keep this output visible too. It is the reference you match against in *Capture the after state*.

    ```bash
    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "docker exec apache_web sh -c 'kill -9 \$(pidof httpd | tr \" \" \"\\n\" | sort -n | head -1)'"
    ```

    <p align="left">
    <img src="https://colony-recorder.s3.us-west-1.amazonaws.com/files/2026-08-31/0ddf3aab-0e56-48ba-a337-c5d16a88380f/user_cropped_screenshot_45f46abe9e6347daa37f8a58127ebeb3_text_export.jpeg" alt="" width="600" />
    </p>

    This reaches inside the container and kills Apache outright, without a graceful shutdown. `pidof httpd` lists every Apache process. The lowest PID is the parent, and `kill -9` ends it immediately.

    - **The command prints nothing, and that is the expected result.** No confirmation message appears; the evidence that anything happened arrives in the steps that follow.
    - Inside the container, tini (PID 1) exits once its child dies, so Rancher sees the container exit unexpectedly. That is the trigger `restart: always` waits for.

### **Wait about 10 seconds**

4. Do nothing for the moment. Rancher notices the exit and starts the container again on its own; 8 to 12 seconds is enough.

    - This pause is the substance of the demonstration.
    - During those seconds the platform repairs itself with no human intervention whatsoever.
    - You have not run `docker start`, and no alert has fired.

7. Compare it against what you noted in *Capture the before state*. Two things must have changed:

    | Field | Before | After | What it proves |
    |---|---|---|---|
    | `restartCount` | *n* | *n* + 1 | Rancher performed exactly one restart |
    | `StartedAt` | original timestamp | ~10 seconds later | This is a new process, not the old one recovering |

    **A `restartCount` higher by exactly one is the result this demo sets out to produce.** It is Rancher's own record that it detected an unexpected exit and acted upon it without a human in the loop. Self-healing is thereby demonstrated as a measured fact — and it works because of a single line written back in Module 1 Step B: `init = true`.

    Put together, the run looks like this (from the workshop's reference output):

    ```
    Before:  StartedAt=2026-05-04T20:46:37Z  restartCount=0
    Crashed httpd inside (kill -9 inside the tini-wrapped container)
    Waited 8s
    After:   StartedAt=2026-05-04T20:47:29Z  restartCount=1   <- Rancher restarted it
    GET http://localhost:8080/   200  <- automatic recovery confirmed
    ```

    ??? warning "TROUBLESHOOTING: the container stays `Exited (137)` and never comes back"
        Two possible causes:

        - You used `docker stop` or `docker kill` from outside. The daemon treats those as deliberate user stops; `restart: always` is for unexpected exits only.
        - You killed PID 1 from inside (`docker exec apache_web kill -9 1`). Linux protects PID 1 of a PID namespace from SIGKILL; without tini, httpd-as-PID-1 is immune.

        **Fix**: make sure the container has `init = true` (set in Module 1) so Rancher injects tini as PID 1, then crash the app with the exact *Crash httpd inside the container* command. Restart the stopped container with `docker start apache_web` first if it is still down.

## **iv. RECOVERY PROCEDURES**

The restart policy handles exactly one failure mode: a crashed process. A bad image, a broken config, lost data, or a dead host each need a real recovery procedure. The essentials follow. Recall that Module 1 Step G had Bob write a full disaster-recovery runbook into your own repository at `infra/RUNBOOK.md`; that document describes your actual host, image tags, and volumes.

These are reference procedures for when something actually breaks rather than steps to run now. Everything below goes in the Bob IDE terminal: Terraform and Ansible commands run from the lab folder on your laptop, and anything wrapped in `ssh` executes on the server.

---

### **Roll back a bad container image**

1. The image tag is the only thing that needs to change. Edit `terraform.tfvars` (e.g. `grafana_image = "grafana/grafana:10.4.2"` back to `:10.4.1`), then apply with a target to limit the blast radius:

    ```bash
    cd infra/terraform
    terraform plan -target=module.monitoring -out=rollback.plan
    # The plan must show ONLY the grafana image + container being replaced.
    # If any volume appears in the plan, abort and investigate.
    terraform apply rollback.plan
    ```

    The operation takes about 90 seconds, and the named data volumes (`prometheus_data`, `grafana_data`, `loki_data`) are left untouched by a container replacement.

    If the bad change was an Ansible-rendered file instead (a broken `prometheus.yml` or Traefik route), restore the template from git and re-run `site.yml --tags content`. Traefik re-reads `routes.yml` automatically (file provider, `watch=true`); Prometheus needs a `docker restart prometheus` to pick up a new config.

---

### **Back up the data volumes**

2. Back up before **any** destructive operation. The pattern uses a throwaway busybox container so nothing extra needs to be installed on the host:

    ```bash
    ssh -p $SSH_PORT -i "$SSH_KEY" ${SSH_USER}@${TARGET_HOST} "
    docker run --rm \
        -v prometheus_data:/data:ro \
        -v /var/backups/lab:/backup \
        busybox \
        tar czf /backup/prometheus_data_\$(date +%Y%m%d_%H%M%S).tar.gz -C /data .
    "
    ```

---

3. Repeat with `grafana_data` and `loki_data`, then `scp` the archives to your laptop.

    !!! warning "GRAFANA CANNOT BE BACKED UP LIVE"
        Prometheus and Loki are mostly safe to back up while running (worst case: the last couple of minutes of data). Grafana's SQLite database is the exception: a live backup can produce a corrupt database. Always stop Grafana before backing up `grafana_data`.

---

### **Restore a volume**

4. Stop the owning container and disable its restart policy so it stays down.

    - On the server (over `ssh`): `docker stop grafana && docker update --restart=no grafana`
    - Untar the archive into the volume with the same busybox pattern as the backup, with the mounts reversed (`-v grafana_data:/data -v /var/backups/lab:/backup:ro`, then `rm -rf /data/* && tar xzf ...`)
    - Bring it back **via Terraform**, which also restores the correct restart policy. From `infra/terraform/` on your laptop:
   `terraform apply -target=module.monitoring.docker_container.grafana`

---

### **Full rebuild**

5. For a new or wiped host, the whole platform comes back from code. From the project root on your laptop:

    ```bash
    ssh-keyscan -p $SSH_PORT $TARGET_HOST >> ~/.ssh/known_hosts
    cd infra/ansible && ansible-playbook -i inventory.ini site.yml     # ~10 min cold
    export TF_VAR_grafana_admin_password='...'
    cd ../terraform && terraform init && terraform apply               # ~3 min
    eval "$(terraform output -raw ssh_tunnel_command)"
    ```

    - Expected RTO is **15–20** minutes.
    - RPO is the age of your last volume backup — and if no backup was ever taken, the metrics, dashboards, and logs are unrecoverable.

## **v. KEY TAKEAWAYS**

- `docker stop` and `docker kill` never trigger a restart policy; the daemon treats them as deliberate stops.
- Linux protects PID 1 from SIGKILL, so `init = true` — set back in Module 1 — is what makes an unexpected crash possible.
- A `restartCount` higher by exactly one is the measured proof of self-healing. No change or more than one restart each signal a different failure.
- A restart policy covers a crashed process alone. A bad image, a broken config, lost data, or a dead host each require a recovery procedure.
- Roll back an image with a targeted plan, and abort if any volume appears in it.
- Back up before any destructive operation, and stop Grafana first; its SQLite database cannot be backed up live.
- A full rebuild from code carries an RTO of 15–20 minutes, and the RPO is the age of the last volume backup.
