### **Clear pre-existing host breakage**

TechZone Ubuntu images frequently arrive with a half-configured `shim-signed` package. Its post-install script tries to mount an EFI partition that does not exist on a cloud VM, so it fails on **every** apt operation. Ansible then cannot install the packages Rancher Desktop needs, its service never starts, and you end up debugging two failures that look like one.

Thirty seconds spent now avoids all of it. Run this before you deploy:

```bash
ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} '
  sudo dpkg --configure -a
  sudo apt-get install -f -y
  sudo dpkg --audit
  echo "dpkg state: clean"
'
```
!!! warning "NEVER REMOVE `shim-signed`"
    It is a protected, boot-critical package and `dpkg` refuses to remove it. It is also entirely unrelated to Rancher Desktop. `dpkg --configure -a` completes its configuration and clears the error state, and that alone is the fix.

    You need not check for Rancher Desktop on the server. Ansible installs it in the next section if it is missing.

`dpkg --audit` printing nothing before `dpkg state: clean` means the package manager is healthy and the deployment will run straight through. This is idempotent — on a host that was already fine it changes nothing.

### **Create `terraform.tfvars`**

Module 1 generated `infra/terraform/terraform.tfvars.example`, a template rather than the real file. Terraform needs the real one. Four variables have no default (`target_host`, `ssh_user`, `ssh_private_key_path`, `domain`), and `ssh_port` defaults to `22` rather than your TechZone port.

Your `TARGET_HOST` and `SSH_USER` exports do not help here: Terraform reads **only** environment variables prefixed `TF_VAR_`, which is why `TF_VAR_grafana_admin_password` is the one that works without a file. Without this step, `terraform apply` stops to prompt for four values and the non-interactive Bob Shell run fails partway through.

Paste this in the Bob IDE terminal, from the lab folder:

```bash
cat > infra/terraform/terraform.tfvars <<EOF
target_host          = "$TARGET_HOST"
ssh_user             = "$SSH_USER"
ssh_port             = $SSH_PORT
ssh_private_key_path = "$(cd "$(dirname "$SSH_KEY")" && pwd)/$(basename "$SSH_KEY")"
domain               = "localhost"
grafana_admin_user   = "labadmin"
EOF
cat infra/terraform/terraform.tfvars
```

!!! warning "`terraform.tfvars` IS SECRET-ADJACENT — NEVER COMMIT IT"
    It carries your server address, SSH user and key path. Module 1 Step D generated a gitignore template covering it; confirm `terraform.tfvars` is listed there before any `git add`.

Read back what it printed. Three things must be right:

- **`grafana_admin_password` is absent.** It stays in `TF_VAR_grafana_admin_password` so your password never lands on disk. Do not add it here.
- **`ssh_private_key_path` is absolute.** Terraform runs from `infra/terraform/`, so a relative `./key.pem` resolves to the wrong place and the provider cannot reach the Rancher socket on the remote host.
- **`domain` is `localhost`.** You arrive through an SSH tunnel as `localhost`, and a real domain in a Traefik `Host()` rule matches nothing — you would get a 404 from a stack whose containers all look healthy.

## **iv. THE DEPLOYMENT PROMPT**

Use the prompt below **exactly** in Bob Shell. If your CLI supports context attachment, attach the inventory using `@infra/ansible/inventory.ini`. There is neither a `make deploy` target nor a wrapper script; the prompt itself performs the deployment.

!!! info "LAUNCH BOB SHELL FROM THE BOB IDE TERMINAL"
    Start Bob Shell in the same terminal session you just ran the pre-flight in, so it inherits your five environment variables. The prompt below references `${TARGET_HOST}`, `${SSH_KEY}` and the rest; in a fresh session those are empty and the run fails at the first step.

!!! note "THE `${...}` PLACEHOLDERS STAY UNEXPANDED, AND THAT IS EXPECTED"
    Exporting a variable makes it available to programs Bob runs. It does not rewrite text you paste. A shell only expands `${TARGET_HOST}` when the shell itself reads the line, and pasting into Bob's input box is not that, so Bob receives the literal characters `${TARGET_HOST}`.

    That is why the first instruction in the prompt tells Bob to read the values out of its own environment. Without it, Bob sees a template full of blanks. It then stops halfway through the run to ask you for the host, the user, the port, and the key path.

The prompt pins everything down. It specifies which key and port every call must use, the exact steps in order, the hard constraints, and what to report back. That precision is what makes the run repeatable, and it is the run from which the expected output (below) was produced.

{% raw %}
```text

Goal: deploy and validate the full containerized web platform on a remote Ubuntu host that exposes ONLY SSH. All web access is via SSH local-forward tunnels from my laptop - no public ports are opened on the cloud side.

The Terraform docker provider host MUST be `ssh://${SSH_USER}@${TARGET_HOST}:${SSH_PORT}` using the same key, with `IdentitiesOnly=yes` in `ssh_opts`.    - Run `terraform fmt -check`, `terraform validate`, `ansible-lint`. Stop on any error.

2) Bootstrap (Ansible - host preparation)
   - cd infra/ansible
   - ansible-playbook -i inventory.ini site.yml --tags bootstrap

   - Confirm every bind-mount source is an absolute directory under /opt/lab on the remote host. If one names a file (index.html, prometheus.yml) or uses path.module, stop and report it: Docker creates a missing file source as a directory of that name and the container dies with "not a directory". That is a Part 1 defect, not something to patch here.
   - Run `terraform output` and capture the values it prints; use those URLs in step 8 rather than re-typing them from this prompt.

4) Configure (Ansible - content)

   - ansible-playbook -i inventory.ini site.yml --tags content
   - Re-run with `--check --diff` and confirm 0 changed (idempotency proof).

5) Open SSH tunnels (in the background, from this laptop)

       8080 -> 127.0.0.1:80           (app via Traefik)
       8081 -> 127.0.0.1:8080         (Traefik dashboard)
       3000 -> 127.0.0.1:3000         (Grafana)
       9090 -> 127.0.0.1:9090         (Prometheus)

       ssh -i ${SSH_KEY} -p ${SSH_PORT} -fN -o ExitOnForwardFailure=yes \

   - curl -fsS http://localhost:9090/-/healthy    -> 200 (Prometheus)

   a deliberate user stop and `restart: always` will not fire. To prove real self-healing,
   crash the application process from INSIDE the container so the exit looks unexpected to
   the daemon. This requires `init = true` on the container (set in Part 1 Step B) so PID 1
   is `tini` and the application is PID 2+ - Linux protects PID 1 from SIGKILL inside its
   own PID namespace, so without tini, killing the in-container app from within is a no-op.

   - Capture before:  `ssh ... docker inspect apache_web -f '{{.State.StartedAt}} restartCount={{.RestartCount}}'`

   - Capture after:   same inspect - `restartCount` must increment by 1 and `StartedAt` must be newer.
   - Re-curl http://localhost:8080/ - must return 200 again automatically.
   - Print the exact crash command you ran. If it contains `docker stop` or `docker kill`, the demo did not prove anything and you must report it as failed.

8) Print the operator URLs and how to tear down
   - Print:
       App        : http://localhost:8080
       Traefik UI : http://localhost:8081
       Grafana    : http://localhost:3000   (<grafana_admin_user> / <masked>)
       Prometheus : http://localhost:9090

       kill $(cat /tmp/lab-tunnel.pid)   # or: pkill -f 'ssh.*-L 8080:127.0.0.1:80'

- Do NOT modify Terraform or Ansible code; only run it. If something is broken, report the file, the defect and the fix, and stop.
- That no-edit rule covers the repository only, never the server. If the host arrives already broken - dpkg/apt failing to configure a pre-existing package, a systemd unit in a failed state, the rdd unit hitting its start limit - repairing the host is expected: fix it, state exactly what you ran and why, and continue.
- These are two separate host failures; fixing apt does not fix the second. If the rdd unit is in a failed state after a bad apt run, that is a start-limit rather than a package problem: run `systemctl reset-failed rdd.service`, then `systemctl start rdd.service`. There is no `docker.service` or `docker.socket` on this host - rdd is not socket-activated - so do not try to start them. Never remove or force-reinstall `shim-signed` - it is boot-critical, dpkg refuses it, and it is unrelated to the container engine.
- Do NOT place configuration on the host by hand. No scp of templates, no rendering files into /tmp, no editing anything under /opt/lab over ssh. Every file on that server must arrive through the Ansible playbook. If a play fails, report the failure and stop; a hand-placed file is invisible to `--check` and destroys the idempotency proof this lab exists to demonstrate.
- If the playbook appears to hang, do NOT work around it. Stop and check the inventory first: run `ansible-inventory --list` from infra/ansible. A parse failure there makes Ansible fall back to implicit localhost, and every subsequent task silently targets the laptop instead of the server.
- Never echo TF_VAR_grafana_admin_password to stdout; mask it.
- If any step fails, stop and print the failing command, the last 30 lines of output, and the proposed remediation.
- Never bind any container to 0.0.0.0. The whole point of this lab is the tunnel-only access model.
- A deliverable you cannot produce is a failure, not a skip. Never substitute a different proof for a missing one: a clean terraform plan says nothing about Ansible idempotency.

Deliverables:
- Summarised bootstrap / plan / apply / play log

- Self-healing proof (container down -> back up automatically)
- Tear-down command for the SSH tunnel
```

## **vi. IF THE RUN FAILS**

Each dropdown below is a real failure this deployment can produce, matched to the step that triggers it. Expand the one that matches your symptom.

??? warning "TROUBLESHOOTING: Ansible run fails on `dpkg returned an error code (1)` or Rancher Desktop will not start"
    **Cause** — the server arrived broken; nothing in your code is at fault. TechZone Ubuntu images sometimes ship with a half-configured `shim-signed` package whose post-install script tries to mount an EFI partition that does not exist on the VM. It exits non-zero on **every** apt operation, so the Rancher Desktop install fails. Systemd then retries its unit until it trips its start limit and refuses to come up at all, which is a second, separate failure you must clear even after apt is healthy.

    **Fix** — repair the host, then re-run the play. This is host state rather than repository code, so fixing it does not break the "only run it" constraint:

    ```bash
    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} '
      sudo sed -i "2i exit 0" /var/lib/dpkg/info/shim-signed.postinst
      sudo dpkg --configure -a
      sudo apt-get install -f -y
      sudo systemctl reset-failed rdd.service
      sudo systemctl start rdd.service
      systemctl is-active rdd
    '
    ```


    The last line must print `active`. The `exit 0` neutralises the bootloader-signing hook, which this lab never uses — nothing else on the host depends on it.

??? warning "FIRST: DIAGNOSTICS AT A GLANCE"
    Before chasing a specific symptom, establish the state of the platform:

    {% raw %}
    ```bash
    # What is running on the host? (expect: traefik, apache_web, prometheus, grafana, loki, promtail)
    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "docker ps --format '{{.Names}} {{.Status}} {{.Ports}}'"

    # Recent logs from a container
    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "docker logs traefik --tail 50"

    # What is bound where on the host: every line must show 127.0.0.1, never 0.0.0.0
    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "ss -tlnp | grep -E ':(80|3000|8080|9090)'"

    # Are the SSH tunnels up on the laptop?
    ps aux | grep 'ssh.*-L'

    # Does the app answer through the tunnel?
    curl -v http://localhost:8080/
    ```
    {% endraw %}

??? warning "STEP 1: BOB STOPS AND ASKS YOU FOR THE HOST, USER, PORT OR KEY PATH"
    **Cause**: Bob is reading `${TARGET_HOST}` and friends as literal text. Pasting into a chat box never expands shell variables, no matter what you exported beforehand. Either the prompt's opening "resolve your own context" block was trimmed off the paste, or the variables really are missing from Bob's environment.

    **Fix**: Tell Bob to look them up itself rather than answering by hand, so the values come from the same place every later command uses:

    ```text
    Do not ask me for those values. Read them from your own environment first:
    env | grep -E '^(TARGET_HOST|SSH_USER|SSH_PORT|SSH_KEY)='
    Then continue from step 1.
    ```

    If that prints empty values, Bob Shell was not launched from the terminal where you exported them. Quit Bob Shell, re-export the five variables in the Bob IDE terminal, and start `bob` again from that same session.

    Typing the values into the chat instead works for the current run, but only for the parts Bob types by hand. Any command it writes with a bare `${SSH_KEY}` still resolves against the empty environment, which is why this shows up later as `Permission denied (publickey)`.

??? warning "STEP 2: `permission denied while trying to connect to the Docker daemon socket`"
    **Cause**: The SSH user is not in the `docker` group. Or it is, but the SSH session was opened *before* the group was added, so the session has not picked up the new membership.

    **Fix**: The bootstrap step adds the user to the `docker` group; after that, **the SSH session must be re-established**. Disconnect and reconnect, or have Ansible run `meta: reset_connection` right after the group change. Then verify:

    ```bash
    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "id | grep docker && docker ps"
    ```

??? warning "STEP 3: `Error: Cannot connect to the Docker daemon`"
    **Cause**: Terraform's docker provider cannot reach the remote Docker daemon over SSH.

    **Fix**: Verify direct access first:

    ```bash
    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} docker ps
    ```

    If that fails, Rancher Desktop is not usable on the host yet; re-run the bootstrap step (`ansible-playbook -i inventory.ini site.yml --tags bootstrap`). If it works, check the provider configuration: the host must be `ssh://${SSH_USER}@${TARGET_HOST}:${SSH_PORT}`, with `ssh_opts = ["-i", "<key>"]` if your key is not in `~/.ssh/`:

    ```hcl
    provider "docker" {
      host = "ssh://${var.ssh_user}@${var.target_host}:${var.ssh_port}"
      ssh_opts = [
        "-i", var.ssh_private_key_path,
        "-o", "StrictHostKeyChecking=no",
        "-o", "UserKnownHostsFile=/dev/null",
        "-o", "IdentitiesOnly=yes",
      ]
    }
    ```

??? warning "STEP 3: `terraform init`: NO PROVIDER NAMED `registry.terraform.io/hashicorp/docker`"
    **Cause**: A child module uses `docker_*` resources without declaring `kreuzwerker/docker` in its own `required_providers`. Terraform falls back to the implicit `hashicorp/docker`, which does not exist.

    **Fix**: Add a `versions.tf` to **every** module under `modules/`, with the same `required_providers` block as the root:

    ```hcl
    terraform {
      required_providers {
        docker = {
          source  = "kreuzwerker/docker"
          version = "~> 3.0"
        }
      }
    }
    ```

    Then re-run `terraform init`.

??? warning "STEP 5: TUNNELS OPEN BUT EVERY REQUEST FAILS WITH `administratively prohibited`"
    **Cause**: TCP port forwarding is disabled in the host's sshd. Some TechZone images ship hardened with `DisableForwarding yes` or `AllowTcpForwarding no`. SSH login works fine, but every `-L` forward is rejected: `curl http://localhost:8080` gets nothing and the ssh process prints `channel N: open failed: administratively prohibited`.

    **Fix**: Enable forwarding on the host. Run this in a **separate terminal** on your laptop (not the one running Bob Shell), with the lab environment variables set:

    ```bash
    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} 'printf "DisableForwarding no\nAllowTcpForwarding yes\n" | sudo tee /etc/ssh/sshd_config.d/0-lab-forwarding.conf >/dev/null && sudo sshd -t && sudo systemctl reload sshd && echo FORWARDING_ENABLED'
    ```

    What it does, piece by piece:

    - Writes a drop-in file `/etc/ssh/sshd_config.d/0-lab-forwarding.conf` containing `DisableForwarding no` and `AllowTcpForwarding yes`. The `0-` prefix makes it sort first among the drop-ins, so it overrides any hardened setting that comes later.
    - `sudo sshd -t` test-parses the sshd configuration before anything is applied. If the config were broken it fails here, instead of reloading a bad config and locking you out of the server.
    - `sudo systemctl reload sshd` applies the change with a reload rather than a restart, so existing SSH sessions (including any open tunnel attempt) are not dropped.
    - `echo FORWARDING_ENABLED` only prints if every previous step succeeded. Seeing that word confirms the change.

    Forwarding is checked when a tunnel channel opens rather than when you log in, so after this, re-run the tunnel command (or tell Bob Shell to retry step 5).

??? warning "STEP 5: `bind: Address already in use` WHEN OPENING SSH TUNNELS"
    **Cause**: One of the local ports (8080, 8081, 3000, 9090) is already taken on the laptop.

    **Fix**: Find the listener and kill it, or remap the *local* side of the forward:

    ```bash
    lsof -i :3000

    # Option A: kill the existing listener, then reopen the tunnel

    # Option B: remap the local port
    ssh -i "$SSH_KEY" -p $SSH_PORT -fN -L 13000:127.0.0.1:3000 ${SSH_USER}@${TARGET_HOST}
    # and open http://localhost:13000 instead
    ```

??? warning "STEP 6: TRAEFIK LOGS SPAM `client version 1.24 is too old. Minimum supported API version is 1.40`"
    **Cause**: Traefik's docker-provider client library starts at API 1.24, and modern Rancher Desktop refuses that handshake. Setting a `DOCKER_API_VERSION` environment variable on the container does **not** fix it; the library does not honour it.

    **Fix**: Do not use Traefik's docker auto-discovery on this host. Switch to the file provider, with the routing rules rendered by Ansible into `/opt/lab/traefik/dynamic/routes.yml` and mounted read-only:

    ```yaml
    # Traefik static configuration
    providers:
      file:
        directory: /etc/traefik/dynamic
        watch: true
    ```

    As a further benefit, this removes the need to mount the Rancher Desktop socket into Traefik at all, which is better for the security review from Module 1.

??? warning "STEP 6: EVERY CONTAINER IS `healthy`, BUT APACHE SERVES \"It works!\", TRAEFIK 404s AND GRAFANA HAS NO DASHBOARDS"
    **Cause**: `/opt/lab` is not mounted into the Rancher Desktop VM. Rancher Desktop runs Docker inside a Linux VM, so the daemon resolves every bind-mount source against the **VM's** filesystem, not the Ubuntu host's. Ansible rendered the configs on the host; the daemon looked in the VM, found nothing, and created empty directories in their place. Traefik starts with no routes, Apache falls back to its stock landing page so the `grep "Welcome"` check fails, Prometheus finds no scrape config, and Grafana provisions zero dashboards — while `docker ps` reports every container healthy. This is the most misleading failure in the lab: it looks like success.

    **Fix**: confirm the mount from inside Rancher Desktop rather than from the host.

    ```bash
    # On the host: the file Ansible rendered
    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "cat /opt/lab/web/index.html | head -3"

    # Inside Rancher Desktop: the same path, as the daemon sees it. If this is empty,
    # /opt/lab is not in the VM's mount list and no bind mount in this lab works.
    ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} \
      "docker run --rm -v /opt/lab:/check alpine ls -la /check/web"
    ```

    Add `/opt/lab` to Rancher Desktop's VM mount list as a writable mount, restart Rancher Desktop, then re-run `terraform apply` and `site.yml --tags content`. Re-check with the second command before moving on.

??? warning "STEP 7: SELF-HEAL DEMO DOES NOT FIRE, CONTAINER STAYS `Exited (137)`"
    **Cause**: Two separate traps:

    1. `docker stop` / `docker kill` are treated as **deliberate user stops** by the daemon. `restart: always` only fires on *unexpected* exits.
    2. Even `docker exec apache_web kill -9 1` from inside is a no-op: Linux protects PID 1 of a PID namespace from SIGKILL. Without `tini`, httpd-as-PID-1 is immune.

    **Fix**: The container must have `init = true` (set in [Module 1, Step B](1-1.md){:target="_blank"}) so Rancher injects `tini` as PID 1 and httpd runs as PID 2+. Then crash the app from *inside*, so the exit looks unexpected to the daemon. The full walkthrough is in [Self-Healing & Recovery](3-2.md){:target="_blank"}.

## **vii. KEY TAKEAWAYS**

- Pre-flight is terminal work: confirm the five environment variables, the project layout, the tool versions, and passwordless sudo before Bob Shell ever starts.
- Clear the `shim-signed` package state on a fresh TechZone host first; the alternative is debugging two failures that look like one.
- `terraform.tfvars` must exist with an absolute key path and `domain = "localhost"`, and the Grafana password never lands in it.
- Bob Shell must be launched from the session that exported the variables, since pasting never expands `${...}` placeholders.
- The prompt's constraints forbid editing the repository and require Bob to stop and report on failure; the run either proves each deliverable or fails.
- Every known failure of the run has a troubleshooting entry matched to the step that produces it.
