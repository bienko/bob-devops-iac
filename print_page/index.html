    DevOps Infrastructure as Code with IBM Bob

    i. "Infrastructure as code" paradigm for modern platforms

    Christopher Bienko (AI Enablement GTM Product Manager) introduces the DevOps Infrastructure as Code with IBM Bob curriculum for hands-on enablement. [4 min]

    Most production platforms today are built and operated through automation. Instead of configuring servers by hand, teams describe the desired state of their infrastructure in code and let tools make reality match that description. This practice is known as Infrastructure as Code (IaC).

    Two of the most widely used tools are Terraform, which provisions infrastructure, and Ansible, which configures it. This lab uses both, together with Rancher Desktop, which provides the container engine.

    RANCHER vs. DOCKER — WHY THE MIXED NAMING CONVENTIONS?

    You install one piece of software on the server: Rancher Desktop, running headless (no graphical interface, because the server has no desktop). It ships a daemon binary called rdd, which is what the Ansible role installs and what systemd runs.

    Rancher Desktop provides a Docker-compatible container engine. That is why, throughout this lab, you still type docker ps, Terraform still uses the kreuzwerker/docker provider, and the socket is still /var/run/docker.sock. "Docker" here names the interface, not a second product. Nothing in this lab installs Docker Desktop or Docker CE.

    So when you read these pages:

    When you see It means
    Rancher Desktop the software installed on the server — installing it, its systemd service, its VM, its version
    rdd the literal daemon binary and systemd unit name, nothing more
    Docker the interface Rancher Desktop exposes — the docker command, Docker networks and volumes, restart policies, /var/run/docker.sock, the kreuzwerker/docker provider

    If a sentence is about what is installed, it says Rancher Desktop. If it is about what you type or what the code declares, it says Docker. There is no third thing.

    Even with mature tooling, building a platform still involves real challenges:

    • Designing an architecture that is secure by default
    • Keeping code modular, idempotent, and reviewable
    • Handling secrets without leaking them into code or state
    • Reasoning about drift, blast radius, and rollback
    • Producing runbooks and documentation that stay current

    It is precisely these challenges that IBM Bob was designed to address.

    This lab is designed for DevOps engineers, platform engineers, SRE teams, and cloud architects. Anyone comfortable with a terminal can follow along, however.

    iii. Environment: the web platform

    The platform you build in this hands-on lab is four containers on a private Rancher Desktop network, provisioned by Terraform and configured by Ansible.

    Component Responsibility
    Traefik v2.11 Reverse proxy. The single entry point that receives every incoming request and routes it to the right backend service. It also publishes metrics about the traffic it handles. Docs
    Apache 2.4 The application. The classic open-source web server, here serving a landing page behind Traefik. Docs
    Prometheus Metrics store. A time-series database that collects metrics by scraping HTTP endpoints. Here it scrapes Traefik, so you can see request rates and response codes over time. Docs
    Grafana Dashboards. Turns metrics into charts. It arrives pre-provisioned with Prometheus as a datasource and a ready-made dashboard for the stack. Docs

    This is the standard production pattern. A proxy sits in front and the application behind it. Metrics are collected from the traffic, and dashboards are layered on top.

    The defining constraint: nothing is publicly exposed. Every container binds to 127.0.0.1 on the remote host. The cloud security group allows only SSH inbound. You reach the services from your laptop through SSH tunnels (ssh -L), and secrets live in Ansible Vault rather than in code or Terraform state.

    Best practices built into the code, each verified during the lab:

    • Idempotent Ansible playbooks. Running them a second time changes nothing, which you confirm with make idempotency
    • Modular Terraform (network, traefik, web, monitoring), so each piece can be changed independently
    • A health check and restart policy on every container. In Module 3 you kill a container and watch Rancher's restart policy bring it back
    • Full rebuild from code alone. No configuration lives outside the repository

    iv. Architecture

    The lab uses two machines: your laptop and one remote Ubuntu server. Everything runs on the server, inside four containers. Your laptop only sends commands and displays the dashboards.

    Note, however, that the server has no web ports open. Its firewall blocks every incoming connection except SSH on port 2223. To reach the dashboards, you run an SSH command that forwards a few local ports (like localhost:8080) to the server, so the web pages travel inside the SSH connection instead of over the open internet. The diagram below shows that path.

    FOLLOW ONE REQUEST

    You open http://localhost:8080 in your browser. The SSH client picks the request up and carries it, encrypted, through the tunnel to the server. There it hands the request to 127.0.0.1:80, where Traefik is listening. Traefik routes it to the Apache container, and the page comes back the same way. To your browser it all looks local. The only thing that ever crossed the internet was SSH traffic.

    HOW TO READ THE DIAGRAM

    There are three parts, read from top of the diagram to the bottom:

    1. "Your Laptop" (left box): where you sit. You browse to normal-looking addresses like http://localhost:8080. Those pages are not served by your laptop: an SSH command you'll run during the lab forwards those ports over to the server behind the scenes.

    2. "Cloud Firewall" (middle): the server's only door. It lets SSH in (port 2223) and blocks everything else, so none of the web services are directly reachable from the internet.

    3. "Remote Ubuntu Server" (right box): where everything actually runs. It has two layers:

      • The 127.0.0.1 row lists the ports the containers are published on. 127.0.0.1 means "this machine only": those ports answer the server itself (and your SSH tunnel, which arrives as the server), but never the outside world.
      • The private Rancher network at the bottom holds the four containers. The arrows show who talks to whom: Traefik passes web requests to Apache, Prometheus pulls metrics from Traefik, and Grafana reads its charts from Prometheus.

    A WORD ON WORKING WITH GENERATIVE AI

    IBM Bob is powered by generative AI and LLMs, and a defining trait of these systems is that they are non-deterministic — unlike the deterministic tools most developers are accustomed to. In practice, that means the same prompt can produce different code from one run to the next. This is both a strength and a quirk of the technology, and it is something to work with rather than against.

    Precision is what tips the odds in your favor. The more clearly you describe what you want, the more closely Bob's output will mirror your intent; conversely, the smallest change in wording can meaningfully change the generated code. Throughout this lab, your results may differ from the solutions shown — and that is expected, not a defect. Whenever an output diverges, you have three good options: refine the prompt and try again, edit the generated code by hand, or simply proceed if the variation still compiles and runs. Human review remains essential at every step, and never more so than while you are still learning the tool.

    You always stay in control. Bob proposes the architecture, generates the code, and runs the deployment. At every step, however, you review and approve what it produced before anything touches the server. This is the same discipline you practiced throughout the AI Maturity Curve course.

    The lab repository begins with little more than a README file and the two workshop walkthroughs. Everything else is written by Bob during the lab, then reviewed and approved by you.

    The code (Module 1). Using Bob IDE, you will build:

    • An architecture document with a diagram
    • Modular Terraform: network, traefik, web, and monitoring modules
    • Ansible roles that install the container engine and render every service config
    • Secrets encrypted with Ansible Vault
    • A security and compliance review of the generated code
    • Log aggregation with Loki and Promtail added to the monitoring stack
    • A disaster recovery runbook
    • A GitHub Actions pipeline, plus a Makefile that runs the same checks locally

    The platform (Module 2). Using Bob Shell, you deploy that code to the remote server. Bob bootstraps the host with Rancher Desktop and creates the network and containers with Terraform. It then renders the configs with Ansible, opens the SSH tunnels, and validates every endpoint. The result is the four-container stack from section iii, live and reachable from your browser.

    The proof (Module 3). You then operate what you built. You read the Grafana dashboards and query Prometheus. You kill a container and watch it self-heal, and you run a recovery drill from the runbook Bob wrote.

    ii. WHY A NAIVE CRASH DEMO FAILS

    Two facts make a naive "kill the container" demo fail, and both were designed around back in Module 1.

    1. docker stop and docker kill do not trigger the restart policy. Docker treats them as deliberate user stops, and restart: always fires only on unexpected exits. Stop the container from outside and it remains in the Exited (137) state indefinitely. To prove real self-healing, the crash has to come from inside the container so the exit looks unexpected to the daemon.

    2. Linux protects PID 1 of a PID namespace from SIGKILL. Even from inside, docker exec apache_web kill -9 1 is a no-op: if httpd runs as PID 1, it is immune. This is why Module 1 Step B rule (e) set init = true on the web container: Rancher injects tini as PID 1 (the init flag) and httpd becomes PID 2+, which can be killed. When httpd dies, tini exits with the same status, the daemon sees an unexpected crash, and restart: always brings the container back in a few seconds.

    iii. RUNNING THE DEMO

    THE DEMO WAS MADE POSSIBLE IN MODULE 1

    Without init = true, nothing can be done at demo time to make this work — the remedy is a Terraform change and a re-apply. That single line is what makes the crash possible at all.

    The demo consists of six short steps, all pasted into the Bob IDE terminal. You capture the before state and confirm the app is up. You crash it and wait. You then confirm the app is back, capture the after state, and compare.

      It prints two things: when the Apache container last started, and how many times Rancher has restarted it since it was created.

      2026-05-04T20:46:37Z restartCount=0

      WRITE DOWN YOUR restartCount

      Your starting value depends on how many times the container has already come up; the screenshot above shows 4. The absolute number is unimportant. What matters is that it has increased by exactly 1 by the end of the demo.

No change means the crash never registered as unexpected and the restart policy did not fire. More than +1 means the container is crash-looping — coming up broken and dying again each time — which is a failure that resembles a success at first glance.

      ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "docker exec apache_web sh -c 'kill -9 \$(pidof httpd | tr \" \" \"\\n\" | sort -n | head -1)'"

      • The command prints nothing, and that is the expected result. No confirmation message appears; the evidence that anything happened arrives in the steps that follow.
      • Inside the container, tini (PID 1) exits once its child dies, so Rancher sees the container exit unexpectedly. That is the trigger restart: always waits for.

    1. Run the exact command from Capture the before state again:

      ssh -i "$SSH_KEY" -p $SSH_PORT ${SSH_USER}@${TARGET_HOST} "docker inspect apache_web -f '{{.State.StartedAt}} restartCount={{.RestartCount}}'"

    1. Compare it against what you noted in Capture the before state. Two things must have changed:

      Field Before After What it proves
      restartCount n n + 1 Rancher performed exactly one restart
      StartedAt original timestamp ~10 seconds later This is a new process, not the old one recovering

      A restartCount higher by exactly one is the result this demo sets out to produce. It is Rancher's own record that it detected an unexpected exit and acted upon it without a human in the loop. Self-healing is thereby demonstrated as a measured fact — and it works because of a single line written back in Module 1 Step B: init = true.

      Put together, the run looks like this (from the workshop's reference output):

      Before:  StartedAt=2026-05-04T20:46:37Z  restartCount=0
Crashed httpd inside (kill -9 inside the tini-wrapped container)
Waited 8s
After:   StartedAt=2026-05-04T20:47:29Z  restartCount=1   <- Rancher restarted it
GET http://localhost:8080/   200  <- automatic recovery confirmed
      TROUBLESHOOTING: the container stays Exited (137) and never comes back

      Two possible causes:

      • You used docker stop or docker kill from outside. The daemon treats those as deliberate user stops; restart: always is for unexpected exits only.
      • You killed PID 1 from inside (docker exec apache_web kill -9 1). Linux protects PID 1 of a PID namespace from SIGKILL; without tini, httpd-as-PID-1 is immune.

      Fix: make sure the container has init = true (set in Module 1) so Rancher injects tini as PID 1, then crash the app with the exact Crash httpd inside the container command. Restart the stopped container with docker start apache_web first if it is still down.

    iv. RECOVERY PROCEDURES

    The restart policy handles exactly one failure mode: a crashed process. A bad image, a broken config, lost data, or a dead host each need a real recovery procedure. The essentials follow. Recall that Module 1 Step G had Bob write a full disaster-recovery runbook into your own repository at infra/RUNBOOK.md; that document describes your actual host, image tags, and volumes.

    These are reference procedures for when something actually breaks rather than steps to run now. Everything below goes in the Bob IDE terminal: Terraform and Ansible commands run from the lab folder on your laptop, and anything wrapped in ssh executes on the server.

    Roll back a bad container image

    1. The image tag is the only thing that needs to change. Edit terraform.tfvars (e.g. grafana_image = "grafana/grafana:10.4.2" back to :10.4.1), then apply with a target to limit the blast radius:

      cd infra/terraform
terraform plan -target=module.monitoring -out=rollback.plan
# The plan must show ONLY the grafana image + container being replaced.
# If any volume appears in the plan, abort and investigate.
terraform apply rollback.plan

      The operation takes about 90 seconds, and the named data volumes (prometheus_data, grafana_data, loki_data) are left untouched by a container replacement.

      If the bad change was an Ansible-rendered file instead (a broken prometheus.yml or Traefik route), restore the template from git and re-run site.yml --tags content. Traefik re-reads routes.yml automatically (file provider, watch=true); Prometheus needs a docker restart prometheus to pick up a new config.

    Back up the data volumes

    1. Back up before any destructive operation. The pattern uses a throwaway busybox container so nothing extra needs to be installed on the host:

      ssh -p $SSH_PORT -i "$SSH_KEY" ${SSH_USER}@${TARGET_HOST} "
docker run --rm \
    -v prometheus_data:/data:ro \
    -v /var/backups/lab:/backup \
    busybox \
    tar czf /backup/prometheus_data_\$(date +%Y%m%d_%H%M%S).tar.gz -C /data .
"

    1. Repeat with grafana_data and loki_data, then scp the archives to your laptop.

      GRAFANA CANNOT BE BACKED UP LIVE

      Prometheus and Loki are mostly safe to back up while running (worst case: the last couple of minutes of data). Grafana's SQLite database is the exception: a live backup can produce a corrupt database. Always stop Grafana before backing up grafana_data.

    Restore a volume

    1. Stop the owning container and disable its restart policy so it stays down.

      • On the server (over ssh): docker stop grafana && docker update --restart=no grafana
      • Untar the archive into the volume with the same busybox pattern as the backup, with the mounts reversed (-v grafana_data:/data -v /var/backups/lab:/backup:ro, then rm -rf /data/* && tar xzf ...)
      • Bring it back via Terraform, which also restores the correct restart policy. From infra/terraform/ on your laptop: terraform apply -target=module.monitoring.docker_container.grafana

    Full rebuild

    1. For a new or wiped host, the whole platform comes back from code. From the project root on your laptop:

      ssh-keyscan -p $SSH_PORT $TARGET_HOST >> ~/.ssh/known_hosts
cd infra/ansible && ansible-playbook -i inventory.ini site.yml     # ~10 min cold
export TF_VAR_grafana_admin_password='...'
cd ../terraform && terraform init && terraform apply               # ~3 min
eval "$(terraform output -raw ssh_tunnel_command)"
      • Expected RTO is 15–20 minutes.
      • RPO is the age of your last volume backup — and if no backup was ever taken, the metrics, dashboards, and logs are unrecoverable.

    v. KEY TAKEAWAYS

    • docker stop and docker kill never trigger a restart policy; the daemon treats them as deliberate stops.
    • Linux protects PID 1 from SIGKILL, so init = true — set back in Module 1 — is what makes an unexpected crash possible.
    • A restartCount higher by exactly one is the measured proof of self-healing. No change or more than one restart each signal a different failure.
    • A restart policy covers a crashed process alone. A bad image, a broken config, lost data, or a dead host each require a recovery procedure.
    • Roll back an image with a targeted plan, and abort if any volume appears in it.
    • Back up before any destructive operation, and stop Grafana first; its SQLite database cannot be backed up live.
    • A full rebuild from code carries an RTO of 15–20 minutes, and the RPO is the age of the last volume backup.

    iii. DESIGN PRINCIPLES

    1. Zero-trust networking

    Principle: No services are exposed to the public internet.

    Implementation:

    • All containers bind to 127.0.0.1 (localhost only)
    • No ports bound to 0.0.0.0 (all interfaces)
    • Access exclusively via encrypted SSH tunnels
    • Firewall only allows SSH inbound

    Benefits:

    • Eliminates attack surface
    • No need for TLS certificates
    • Simplified security posture
    • Compliance-friendly

    2. Infrastructure as code

    Principle: All infrastructure is defined in version-controlled code.

    Implementation:

    • Terraform manages Docker resources via the kreuzwerker/docker provider
    • Ansible manages host configuration
    • Git tracks all changes
    • CI/CD validates before deployment

    Benefits:

    • Reproducible deployments
    • Auditable changes
    • Disaster recovery ready
    • Environment parity

    3. Observability first

    Principle: Comprehensive monitoring and logging from the first deployment onward.

    Implementation:

    • Prometheus for metrics collection
    • Grafana for visualization
    • Loki for log aggregation
    • Pre-configured dashboards

    Benefits:

    • Proactive issue detection
    • Root cause analysis
    • Performance optimization
    • SLA compliance

    4. Self-healing

    Principle: Automatic recovery from failures.

    Implementation:

    • Docker restart policies (always)
    • Health checks on all containers
    • Init system (tini) for proper signal handling
    • Automated monitoring and alerting

    Benefits:

    • Reduced downtime
    • Lower operational burden
    • Improved reliability
    • Faster recovery

    • No password authentication

    • All access logged
    • Metrics collected
    • Anomaly detection ready

    Data exfiltration No outbound restrictions (accept risk) Medium
